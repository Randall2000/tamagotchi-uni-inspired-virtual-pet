## 0. 如何使用這份文件

這是可供產品、設計、韌體、遊戲程式與測試人員共同執行的規格。所有「應」代表正式需求；「建議」、「預設」、「候選」代表可在 Sprint 0／設計評審修改的提案，不得把提案誤認為現成功能。

- **優先級**：P0＝核心 MVP 必須；P1＝豐富化；P2＝硬體感知及裝置互連；P3＝連網服務。
- **里程碑**：M0 技術／授權審核、M1 平台骨架、M2 可玩核心、M3 養成深度、M4 生活擴充、M5 實體機、M6 線上功能。
- **驗收 ID**：`AC-<模組>-<流水號>`；每項必須具備測試步驟、預期結果、執行證據及 Passed/Failed/Blocked 狀態。
- **完成定義**：Demo 能玩、單元測試通過、異常路徑處理完畢、文件更新、沒有 Critical/High 阻擋問題，才可宣告 Done。
- 本文件 **不表示程式已建立或測試已通過**；測試需在實際程式／硬體上執行。

## 1. 專案摘要

### 1.1 一句話定位

創作一款受 Tamagotchi Uni **互動方式與養成深度**啟發、採 A/B/C 三按鍵操作的**原創全彩電子寵物**；角色擁有需求、個性、喜好、成長路徑與自發行為，讓玩家可以短時間照顧、長期陪伴。

### 1.2 要解決的問題

1. 直接照搬 Catode32 的黑白 OLED、八鍵與既有遊戲功能，無法充分滿足以 Uni 為基準的體驗。
2. 若先做角色美術和硬體外殼，之後很容易因選單、動畫介面或記憶體限制而返工。
3. 沒有 Mac 可執行版本及時間快轉／狀態注入工具，實際養成流程很難快速反覆驗證。
4. 程式若與 GPIO、顯示 IC、儲存方式耦合，後續 C6→S3 或更換 TFT LCD 就會產生大量重寫。

### 1.3 產品目標

| ID | 目標 | 驗證指標／放行標準 |
|---|---|---|
| G-01 | 三鍵易學 | 未閱讀教學的內部測試者（建議 n≥5），4/5 能在 60 秒內完成一次餵食；首輪未達標需修正導覽 |
| G-02 | 核心可玩 | 從新遊戲→餵食→玩耍→清潔→睡眠→狀態→存檔→重新載入，全流程無阻斷 |
| G-03 | 寵物有生命感 | 閒置 15 分鐘能觀察至少 3 種符合需求／時段的可解釋行為（以加速時間測試） |
| G-04 | 成長具有因果 | 不同照顧策略可重現至少 2 條不同成長結果，且有事件紀錄可解釋原因 |
| G-05 | 核心可攜 | 同一份核心規則在 Mac 與至少一種 ESP32 目標平台共用，不使用編譯目標特定的 GPIO API |
| G-06 | 開發可迭代 | 以佔位素材測完主要流程，正式 Sprite 替換不修改核心業務邏輯 |
| G-07 | 可驗證品質 | P0 的所有 AC 必須通過，CI 全綠、0 件未解 Critical/High 缺陷 |

### 1.4 設計原則

- **Uni 為體驗標竿，不是資產來源**：學習三鍵操作、人格與喜好、照顧循環、家居、裝扮、探索等概念；不複製 Bandai 角色、圖像、UI 素材、音效、文案或商標。
- **先無圖後有圖**：畫面用色塊、矩形、字串與佔位動畫表示；素材以 `asset_id` 綁定。
- **一致、可預測、可回復**：A 選擇、B 確認、C 返回；有明顯選取狀態、音畫回饋、操作失敗原因。
- **低負擔陪伴**：允許短暫離線，不刻意造成高壓／懲罰；離線進度須有明確上限。
- **可測試**：所有時間、亂數、存檔、裝置輸入均可在測試中注入（Clock/RNG/Storage/Input）。

## 4. 產品資訊架構（IA）與三鍵互動

### 4.1 首頁與選單

```text
啟動畫面
├─ 新遊戲 → 初始化角色 → 房間
└─ 繼續遊戲 → 讀取存檔 → 房間

房間（待機／主畫面）
├─ 照顧（P0）
│  ├─ 餵食（食物列表）
│  ├─ 玩耍（P0 簡單互動；P1 小遊戲）
│  ├─ 清潔
│  └─ 休息／熄燈
├─ 狀態（P0）：需求、性格簡介、成長資訊
├─ 道具（P1）：背包、玩具、配件
├─ 房間（P1）：家具、佈置
├─ 外出（P2）：散步、探索、收集
```

在 P0 中，尚未開發的 P1/P2 選項應標示「開發中」且不得導向空畫面；產品發行版可直接隱藏。

### 4.2 按鍵語義（必須全域一致）

| 輸入 | 待機房間 | 選單／清單 | 確認對話框 |
|---|---|---|---|
| `A` 短按 | 開啟主選單／切換最上層選項（由畫面模式決定） | 切換到下一項，末項回第一項 | 切換「是／否」 |
| `B` 短按 | 確認目前選擇／進入選單 | 選擇、確認、觸發互動 | 確認目前選項 |
| `C` 短按 | 關閉提示／不變 | 返回上一層，保留上層游標 | 取消並返回 |
| `A` 長按（預留） | 時鐘／日期畫面 | 不覆蓋既有短按事件 | 不執行危險操作 |
| 其他長按／組合鍵 | **非 P0 必須**，禁止在未完成防誤觸設計前啟用重設／刪檔 | — | — |

**決策**：若房間待機需要第一下 `A` 開選單，進入選單後才用 A 輪選；不可同時承諾待機時「A 開選單」與「A 直接切換未顯示的項目」。

### 4.3 導覽狀態機

- 導覽狀態至少 `Splash | NewGame | Room | MainMenu | SubMenu | Confirm | Feedback | Status | SleepView | Error`。
- 任何非根畫面短按 C，最多一次動作返回上一層；連續按 C 必須能回到 Room（例外：不可取消的原子存檔期間，須顯示狀態）。
- 選項可循環輪選，游標清楚標示；禁用項不可被 B 執行。
- 動作執行中重複按 B 不得重複扣道具或重複給獎勵。
- 應提供「無項目」、「背包滿」、「沒錢」、「狀態不允許」等文字回饋，不可靜默失敗。

## 5. 功能詳細規格與驗收條件（P0）

下列 AC 均要求對應測試證據：自動化測試輸出、螢幕錄影／截圖、事件日誌或裝置測量；單純目視宣稱完成不算通過。

### FR-01｜開局、角色初始化（P0 / M2）

**需求**：玩家可以建立 1 個本機存檔；預設 1 隻初始寵物，採用匿名原創 `species_id` 與佔位圖。初始數值與時區由可版本化的設定載入。建立新遊戲不得覆蓋現有存檔而不提示。

- `AC-INIT-01`：無存檔啟動，顯示「新遊戲」；按 B 後在 3 秒內進入 Room，所有初始數值在合法範圍。
- `AC-INIT-02`：有存檔啟動，預設聚焦「繼續」；C/取消不會更動存檔。
- `AC-INIT-03`：已有進度再按「新遊戲」，需顯示不可誤觸的覆蓋確認；選「否」後檔案雜湊不變。
- `AC-INIT-04`：同一 `seed`、`initial_config`、`clock` 建立兩份新遊戲，其初始狀態相同。

### FR-02｜三鍵輸入與導覽（P0 / M1–M2）

**需求**：遊戲只認識抽象事件 `KeyA`, `KeyB`, `KeyC`，硬體／鍵盤映射在適配器處理。應有去彈跳、短按／長按分離與重複輸入保護。

- `AC-INPUT-01`：Mac 使用指定三顆鍵（建議 `J= A`, `K= B`, `L= C`，可設定），達成與實體三鍵相同效果。
- `AC-INPUT-02`：模擬 30ms 以下接點抖動，每次實際按壓最多觸發 1 個短按事件；測試參數可設定。
- `AC-INPUT-03`：A 可以循環遍歷 10 項選單，10 次切換後返回同一項，無游標越界。
- `AC-INPUT-04`：C 可從深度 ≥3 的選單逐層回 Room；返回後既有數值不變。
- `AC-INPUT-05`：快速連按 B 5 次觸發一次不可重複交易（idempotent transaction）。
- `AC-INPUT-06`：長按門檻預設 600ms（可配置）；長按不在釋放時額外觸發短按。

### FR-03｜需求與狀態（P0 / M2）

**需求**：核心需求 `satiety(飽足)`, `happiness(心情)`, `hygiene(清潔)`, `energy(精力)`, `health(健康)`, `bond(親密)` 均在 0..100。特質／喜好另外儲存；不要把「餓」與「飽」混用造成數值方向相反。

**初始預設（可調參數）**：飽足 70、心情 70、清潔 80、精力 80、健康 100、親密 30。狀態衰減由配置表與 `GameClock` 共同計算，不在 UI 每幀直接扣數值。

- `AC-STAT-01`：任意合法或極端動作序列，六項需求永遠在 0..100。
- `AC-STAT-02`：餵食使飽足上升且食物數量正確減 1；不會超過 100。
- `AC-STAT-03`：玩耍可提高心情並消耗精力（具體量由平衡表提供），事件原因可追溯。
- `AC-STAT-04`：清潔能改善清潔值；非必要條件時不得出現負數或溢位。
- `AC-STAT-05`：需求低於警示門檻（預設 ≤25）會產生對應提示；恢復至解除門檻（預設 ≥35）才消失，避免提示抖動。
- `AC-STAT-06`：以快轉 24h 的測試可精準再現設定值對應的需求變化；同初始狀態結果一致。

### FR-04｜照顧操作與回饋（P0 / M2）

**需求**：首版至少支援餵食、玩耍、清潔、休息、查看狀態。每次互動產生事件、影響數值並播放佔位動畫／文字回饋。全部由 B 確認、C 返回。

- `AC-CARE-01`：在 Room 使用 A/B/C，30 秒內可完成一次餵食，畫面有成功提示且飽足度實際變更。
- `AC-CARE-02`：食物為 0 時餵食不可成功；不扣數值，顯示「沒有食物」。
- `AC-CARE-03`：餵食使用一次性事件 `interaction_id`；連按、重送或畫面重繪不得重複執行。
- `AC-CARE-04`：玩耍成功後同時出現快樂反應與數值變動；精力太低時需有合理回饋。
- `AC-CARE-05`：清潔成功後 `hygiene` 提升，房間狀態提示隨之更新。
- `AC-CARE-06`：使用休息指令後可進入/離開睡眠流程；不應讓主選單仍提供被禁止的照顧操作。
- `AC-CARE-07`：狀態頁至少顯示六項需求的名稱與可讀數值／圖示，C 返回原畫面。
- `AC-CARE-08`：所有失敗操作都可找到失敗原因，不會只播放成功動畫卻未更新資料。

### FR-05｜時間、作息與離線推進（P0 / M2–M3）

**需求**：真實時鐘與遊戲推進解耦。使用注入的 `Clock`；儲存 `last_simulated_at`。每次載入計算正向經過時間，採分段或解析解推進，避免逐秒回放。**提案**：一次離線推進上限 48h（需經平衡測試後定案）；回撥時鐘不能倒扣或獲取額外獎勵。

- `AC-TIME-01`：同一存檔與相同注入時間，重複載入結果一致。
- `AC-TIME-02`：離線 6h 後重新載入，需求與作息正確更新，沒有逐幀補播導致卡頓。
- `AC-TIME-03`：離線 7 天時只依設定上限（預設 48h）推進；不可無限衰減而導致不可逆崩壞。
- `AC-TIME-04`：系統時間向後調整 4h，遊戲推進為 0 並記錄 clock anomaly，不得產生負年齡。
- `AC-TIME-05`：以 Debug 快轉 1h／24h／7d 時，不修改 Mac 真實系統時間。
- `AC-TIME-06`：睡眠時段與日夜標示由時區與設定導出；跨午夜／日光節約變更有測試。

### FR-06｜自主行為 AI（P0 / M3）

**需求**：用有限狀態機 + Utility Scoring（或等效可解釋規則）決定行為，**不是只隨機輪播動畫**。至少支援 `idle`, `walk`, `inspect`, `play_alone`, `seek_food`, `seek_attention`, `rest`, `sleep`, `groom`, `react_happy`, `react_unhappy`, `react_favorite`。需具備優先權、冷卻期與玩家互動中斷規則。

**預設行為選擇**：睡眠／嚴重需求 > 玩家互動回應 > 高需求行為 > 個性偏好 > 閒置；當多個候選分數接近時可使用可重現 seed RNG。不可在每幀全盤重抽造成抖動。

- `AC-AI-01`：寵物在飽足 ≤25 且非睡眠的條件下，比健康狀態更常選擇 `seek_food`；可用 100 個固定 seeds 驗證頻率方向。
- `AC-AI-02`：精力 ≤20 且沒有更高優先級事件時，下一次決策偏好 `rest/sleep`。
- `AC-AI-03`：同一 `state + clock + seed + event history` 產生完全一致的行為序列。
- `AC-AI-04`：在「非睡眠、需求正常」固定 fixture 中，15 分鐘模擬期間能出現至少 3 種自主行為，且沒有每幀閃爍／無限互切。
- `AC-AI-05`：玩家按 B 觸發互動後，行為引擎按定義打斷／排隊；一次互動只完成一次。
- `AC-AI-06`：單一行為有最長持續時間與冷卻期，不能因條件錯誤永久卡死。
- `AC-AI-07`：每次行為決策可輸出 Debug reason，例如 `energy_low`, `favorite_item_nearby`；正式版可以關閉詳細日誌。
- `AC-AI-08`：所有行為用 `behavior_id` 對接素材，不引用實際 PNG 名稱。

### FR-07｜性格、喜好及成長（P0 / M3）

**需求**：角色擁有可配置的性格傾向（建議 `activity`, `curiosity`, `sociability`, `independence`，0..100）、物品喜好映射與成長歷程。性格對行為權重、互動反應和成長有影響；成長依「照顧品質 + 行為歷史 + 性格偏向」判斷，不直接複製 Uni 特定進化公式。

**成長預設（僅平衡起點）**：幼年→成長→成熟，孵化／初生作為開局演出而非另計成長階段；階段所需遊戲時間由 `growth_rules.json` 設定；初版至少有 2 條成熟型分歧，素材先用不同形狀／顏色表示。成長結果在紀錄中有可解釋的 `growth_reason`。

- `AC-GROW-01`：以同一照顧序列與相同 seed，兩次模擬獲得相同成長結果。
- `AC-GROW-02`：至少兩種不同照顧策略可觸發不同分歧，並產出 `growth_reason`。
- `AC-GROW-03`：成長階段只前進不倒退；時間不足不得跳階；孵化演出不計算成長階段。
- `AC-GROW-04`：對喜好食物與討厭食物的反應有差異（動畫事件或文字反應＋狀態效果）；背包扣除仍正確。
- `AC-GROW-05`：同一需求狀態、不同性格的角色，其自主行為評分存在可測差異。
- `AC-GROW-06`：性格變化與成長快轉可以在 Debug 介面觸發，不必等待現實數天。
- `AC-GROW-07`：切換成長形態只更換 `appearance_id`/素材映射，不改核心狀態資料結構。

### FR-08｜存檔與資料正確性（P0 / M2–M3）

**需求**：建立版本化的 `SaveSnapshot`，Mac 由檔案適配器落地（開發期間可使用 JSON）；ESP32 改由 NVS/Flash 等適配器實現，不要求實體儲存格式與桌面逐 byte 相同。存檔須包含角色、需求、時間、性格、喜好、成長、物品、RNG seed／必要狀態、schema version。

**原則**：寫入採 temporary→flush→atomic rename（適用支援原子 rename 的桌面檔案系統）；保留前一份可恢復的存檔，實機以雙槽或等效策略設計。絕不可在硬體核心規則中直接呼叫 `std::fs`。

- `AC-SAVE-01`：餵食後存檔→關閉→重啟，六項需求、物品數量與成長紀錄完整一致。
- `AC-SAVE-02`：讀取合法存檔時檢查 schema version 與校驗資訊；不支援版本顯示清楚錯誤而不是 panic。
- `AC-SAVE-03`：模擬存檔寫入中斷或截斷，能恢復上一次完整存檔，且不會把壞檔覆蓋到備份。
- `AC-SAVE-04`：測試舊版 schema → 新版 schema 的至少一條 migration，資料沒有無聲遺失。
- `AC-SAVE-05`：在同一存檔上重試已確認完成的交易，不會重複給貨幣／扣食物。
- `AC-SAVE-06`：資料格式不可儲存原版 Catode32 美術／Bandai 專屬識別；本專案使用自有穩定 ID。

### FR-09｜全彩 UI、素材接口與繁體中文（P0 / M1–M3）

**需求**：邏輯畫布 240×240；色彩格式預設 RGB565（16-bit），必要時由平台適配器轉換。UI 與 Game Core 不互相依賴。每個動畫按 `asset_id`, `state`, `direction`, `frame` 查表；不存在素材時用 placeholder，不得當機。繁體中文字型與可讀性須在目標畫布驗證。

- `AC-UI-01`：Mac 視窗顯示 240×240 邏輯畫布，2x／3x／4x 放大時維持整數像素縮放、文字與選單不裁切。
- `AC-UI-02`：主選單選取狀態至少透過高亮／外框／指示符之一清楚辨識，不能只靠色彩差異。
- `AC-UI-03`：所有 P0 介面主要文案均為繁體中文，文字過長時有換行、分頁或截斷策略，不遮擋操作區。
- `AC-UI-04`：缺少任一動畫 `asset_id`，程式顯示預設形狀／文字並記錄警告，不會崩潰。
- `AC-UI-05`：可替換至少 3 組 placeholder 素材而不修改 Game Core 程式碼；視覺事件與資料邏輯分離。
- `AC-UI-06`：重要操作（餵食、存檔、無道具、狀態不足）均有確認／結果回饋，不依賴聲音才能理解。

### FR-10｜Mac 模擬器與 Debug 工具（P0 / M1–M3）

**需求**：Mac Apple Silicon 優先；視窗用 SDL2 或經 Sprint 0 驗證的等效方案。正式產品畫布與 Debug Panel 分離。測試工具可單步更新、時間快轉、指定狀態／性格、固定 seed、查看事件 log、重設測試存檔。

- `AC-DEV-01`：在 Apple Silicon Mac，依 README 安裝並執行指令，乾淨環境可編譯啟動；指令需在 CI 或乾淨測試機驗證。
- `AC-DEV-02`：鍵盤 A/B/C 模擬輸入可完成 P0 全流程；實際鍵盤按鍵對照清楚顯示。
- `AC-DEV-03`：Debug Panel 能修改六項需求與四個性格傾向，Room 畫面下一次刷新可反映。
- `AC-DEV-04`：可以快轉 1h、24h、7d、單步 Tick，不需更改 OS 時鐘。
- `AC-DEV-05`：可設定 RNG seed；重播相同事件時，成長與行為結果可比較且一致。
- `AC-DEV-06`：可以匯出簡潔事件日誌 `timestamp, event_id, old_state, new_state, reason`，不含帳密或個資。
- `AC-DEV-07`：Debug 專屬命令不能由正式版一般三鍵誤觸。
- `AC-DEV-08`：提供至少 5 個固定測試情境：剛出生、飢餓、精力低、進化前、損壞存檔。

## 6. 擴充功能與驗收（P1–P3）

### FR-11｜背包、物品、商店與遊戲貨幣（P1 / M4）

**需求**：物品以 `item_id`、`category`、`stack_limit`、`effect_id` 定義。貨幣採不可為負的整數，商店價格由資料表提供。首版建議至少 5 種食物、3 種玩具、3 種家具、3 種配件；僅用原創佔位資產。

- `AC-ITEM-01`：購買成功時貨幣減少價格、背包增加 1 件；商店交易有唯一 ID 並可防重入。
- `AC-ITEM-02`：貨幣不足、背包容量不足或價格資料異常時，交易全部取消，貨幣與背包都不變。
- `AC-ITEM-03`：使用消耗品成功後，物品數量恰減 1，對應 `effect_id` 只套用一次。
- `AC-ITEM-04`：存檔重開後商品、餘額與背包順序／有效項目不丟失。
- `AC-ITEM-05`：更換不同版本物品表時，未知 `item_id` 走兼容處理，不因資產不存在而崩潰。

### FR-12｜小遊戲與貨幣獎勵（P1 / M4）

**需求**：先實作 1 種完全原創、三鍵即可操作、單局 30–90 秒的小遊戲，輸贏回饋清晰。獎勵配置可調整，防止中斷重送刷幣。

- `AC-GAME-01`：僅用 A/B/C 可完成一局，無必需的方向鍵、觸控或連線。
- `AC-GAME-02`：完成一局只授予一次設定貨幣；重進結果頁不得重領。
- `AC-GAME-03`：局中退出有明確確認，退出後不取得完成獎勵。
- `AC-GAME-04`：10 次固定 seed 測試可以重現相同判分結果。

### FR-13｜房間、家具與配件（P1 / M4）

**需求**：房間使用 `room_id` 與固定槽位定義（如牆面、地面、玩具、裝飾）；寵物可依喜好與擺放物品互動。角色配件和基本動作以獨立圖層呈現，正式美術未完成前使用色塊。

- `AC-ROOM-01`：玩家能更換至少 2 個家具槽位；同一槽位只有一個有效擺件。
- `AC-ROOM-02`：不適用的家具不能放入該槽，錯誤提示明確且不消耗家具。
- `AC-ROOM-03`：擺放喜愛玩具會改變 `react_favorite` 或 `play_alone` 的候選評分，可重現。
- `AC-ROOM-04`：配件啟用／移除後，角色圖層變更，核心性格／狀態不被重設。
- `AC-ROOM-05`：室內配置存檔後重新載入一致。

### FR-14｜散步、材料收集與 DIY（P2 / M5）

**需求**：散步功能先依賴抽象 `MotionSource`，提供模擬步數產生器；實機有對應 IMU 或其他感測器時再介接。配方使用 `recipe_id`，所有合成交易原子化。

- `AC-WALK-01`：在沒有感測器的 Mac 模擬器中，使用固定模擬步數可得到可預期的材料獎勵。
- `AC-WALK-02`：真實硬體若未配置感測器，功能應顯示不可用或使用清楚標示的模擬模式，不得偽稱真實步數。
- `AC-WALK-03`：材料齊全時完成一次 DIY，材料扣除與成品增加同時成功；材料不足時不修改存檔。
- `AC-WALK-04`：不得透過裝置時鐘回撥重複領取每日獎勵。

### FR-15｜近距離裝置互動（P2 / M5）

**需求**：離線裝置間互動（例如 ESP-NOW 或其他適合晶片的通訊）須先有明確相容性設計。第一版限模擬器協定測試，不承諾跨所有板卡能互通。資料交換只包含必要角色資訊／交換物品，不暴露裝置 Wi-Fi 密碼。

- `AC-SOCIAL-01`：配對須雙方明確確認，逾時或取消不新增好友紀錄。
- `AC-SOCIAL-02`：相同交換封包重送不會重複增加道具。
- `AC-SOCIAL-03`：錯誤或版本不兼容封包被拒收並記錄原因，不導致 crash。
- `AC-SOCIAL-04`：未配對裝置不能任意發送狀態修改指令。

### FR-16｜Wi-Fi 更新、線上活動與遠端內容（P3 / M6）

**需求**：網路功能為獨立模組，離線遊戲是預設完整體驗；雲端帳號、OTA、活動、安全與合規需另立安全設計文件後才能上線。不得在 P0 偷渡未授權外部服務或 API Key。

- `AC-ONLINE-01`：關閉網路，P0／P1 玩法仍可使用；沒有永久阻擋畫面。
- `AC-ONLINE-02`：需要網路的選項顯示連線狀態與失敗原因，不會無限轉圈。
- `AC-ONLINE-03`：遠端下載內容需有版本、雜湊或簽章驗證；驗證失敗不得套用。
- `AC-ONLINE-04`：OTA（如實作）必須有回滾策略與中斷復原測試，未通過前不得對外發布。

## 7. 工程架構（跨開發板、先模擬器）

### 7.1 分層及相依規則

```text
            ┌────────────────────────────────────────────┐
            │           Game Application Layer           │
            │ Navigation · Commands · Events · Scene VM  │
            └────────────────────┬───────────────────────┘
                                 │
            ┌────────────────────▼───────────────────────┐
            │              Pure Game Core                │
            │ Pet · Needs · AI · Growth · Economy · Time │
            │ No GPIO / SPI / Wi-Fi / SDL direct imports │
            └────────────────────┬───────────────────────┘
                                 │ interface / traits
        ┌──────────────┬──────────┼───────────┬──────────────┐
        ▼              ▼          ▼           ▼              ▼
    DisplayPort     InputPort   ClockPort  StoragePort     AudioPort
        │              │          │           │              │
    ┌───┴──────────────┴──────────┴───────────┴──────────────┴────┐
    │ Adapters: Mac(SDL2) / ESP32-C6 / ESP32-S3 / future hardware│
    └──────────────────────────────────────────────────────────────┘
```

**硬性約束**：

1. `game-core` 必須可在主機上以 `cargo test` 單獨測試；不可直接依賴 `esp-hal`, `ssd1306`, `mipidsi`, `sdl2`、GPIO 或串口。
2. `GameCore::update(delta, commands, rng)`（示意介面）採確定性狀態轉移，回傳 `events`；不得直接操作螢幕。
3. `GameController` 將 A/B/C 與導航狀態轉成命令；畫面層只消費讀取模型與 `visual_event`。
4. `StoragePort`、`ClockPort`、`RandomPort`、`InputPort`、`DisplayPort` 皆可測試替換；音效及震動可以為 No-Op 適配器。
5. ESP32-C6 與 S3 不共用特定 HAL 實作，但共享事件／導航／核心規則；S3（含 PSRAM 型號）為**優先評估**而非當前已定案硬體。
6. 顯示器邏輯解析度為 240×240；變更硬體顯示器型號只替換平台顯示驅動，若實際畫布不同則需變更 UI layout config，不能保證所有螢幕尺寸零修改。
7. 為避免 ESP32 記憶體限制，應在 M0 決定 `no_std + alloc` 或受控 `std` 策略，並在實機測量 heap/stack；不得假設 macOS 記憶體表現能代表裝置。

### 7.2 目標 Workspace（建議，非既有檔案）

```text
│  ├─ game-assets/          # 佔位素材、manifest、字型映射

│  ├─ desktop-sim/          # Mac SDL2 / debug panel / save
│  ├─ firmware-c6/          # 可選 ESP32-C6 適配

```

**評估 Catode32 重用時，不要直接覆寫 upstream**：先 fork + 固定 commit SHA + 模組依賴清單；分清既有程式、改作內容與原創內容。只有通過授權與技術審查的程式可移入新 Workspace。

### 7.3 領域模型與資料契約（概念）

| Entity | 最少欄位 | 規則 |
|---|---|---|
| `PetState` | `pet_id`, `species_id`, `stage`, `appearance_id`, `needs`, `personality`, `likes`, `age_simulated` | ID 穩定，UI 不依賴圖檔 |
| `Needs` | `satiety`, `happiness`, `hygiene`, `energy`, `health`, `bond` | 整數 0..100 |
| `Personality` | `activity`, `curiosity`, `sociability`, `independence` | 整數 0..100，可平衡調整 |
| `BehaviorState` | `behavior_id`, `started_at`, `deadline`, `cooldown_map` | 可中斷、可復原 |
| `GrowthRecord` | `stage`, `stage_entered_at`, `rule_id`, `growth_reason` | 可追蹤分歧依據 |
| `Inventory` | `items`, `currency`, `applied_transactions` | 不可負值、交易冪等 |
| `WorldState` | `local_timezone`, `last_simulated_at`, `room_id`, `time_of_day` | 以注入 Clock 推進 |
| `SaveSnapshot` | `schema_version`, `saved_at`, `pet`, `world`, `inventory`, `rng_state`, `checksum` | 版本化、備援恢復 |
| `VisualEvent` | `asset_id`, `animation_id`, `message_key`, `priority` | 不包含實體圖檔路徑 |

**命令與事件範例（純示意）**：

```json
{
  "command_id": "cmd-00042",
  "type": "FEED_PET",
  "payload": { "item_id": "food_basic_01" }
}
```

```json
{
  "event_id": "evt-00106",
  "type": "PET_FED",
  "payload": {
    "item_id": "food_basic_01",
    "need_changes": { "satiety": 18 },
    "visual_event": "pet.eat.normal"
  }
}
```

**實作備註**：上面是 domain contract 草案，不要求真實韌體內部一律序列化 JSON；如使用 `serde`，需要評估 embedded 目標大小、記憶體及序列化可靠性。

### 7.4 遊戲時鐘、規則引擎、可重現性

- `WallClock` 提供現實日期／時區；`SimulationClock` 提供遊戲 delta；兩者不可混用。
- 需求變化不綁 FPS，建議每固定遊戲時間步長積分；動畫可獨立渲染更新。
- AI 決策需使用可注入 RNG 並保留可重現 seed／必要狀態；只固定 seed 但改變事件呼叫順序仍可能不同，測試必須固定完整事件順序。
- 時間大幅快轉與分段推進的結果允許依規則有小差異，但必須建立一致性測試與容忍值；同輸入應保證結果一致。
- 所有敏感交易、成長與時間異常都應寫 structured event 便於除錯。

### 7.5 顯示與動畫資產規格

| 類別 | 草案規格 | 驗收方式 |
|---|---|---|
| 畫布 | 240×240，RGB565 | 模擬器與目標 LCD 同座標 |
| UI | 繁體中文、可辨識焦點、無裁切 | 截圖快照＋人工檢查 |
| 基礎角色圖 | 暫用 48×48 / 64×64 佔位方塊 | 渲染器不依賴最終大小 |
| 動畫 ID | `pet.idle`, `pet.walk`, `pet.eat.normal`, `pet.sleep` 等 | 缺 ID 回退，不 panic |
| 正式圖片 | 之後再做獨立 Sprite Sheet、透明色策略、配件圖層 | 資產 Pipeline 單獨驗收 |
| 更新策略 | 優先區域刷新；不假設存在整張 framebuffer | 在裝置上以 profiling 決定 |

### 8.2 跨平台契約的驗收

- `AC-ARCH-04`：更換鍵盤映射／GPIO 腳位時，不需要修改導航狀態機。
- `AC-ARCH-05`：實機於 60 分鐘連續操作與畫面更新後無崩潰、看門狗重啟或持續增長的記憶體使用量（測試條件記錄在案）。

### 10.2 關鍵端到端情境（Gherkin）

**E2E-01：首次照顧**

```gherkin
Given 應用程式沒有任何存檔
When 玩家啟動 Mac 模擬器並選擇「新遊戲」
And 玩家使用 A/B/C 開啟「照顧 > 餵食」並確認食物
Then 顯示原創寵物的進食佔位動畫與成功文案
And 飽足度依設定增加且食物數量減少一份
And 回到房間後，狀態頁可查到新數值
```

**E2E-02：存檔復原**

```gherkin
Given 玩家已完成餵食與玩耍並成功存檔
When 玩家關閉程式後重新開啟選擇「繼續遊戲」
Then 角色 ID、需求、性格、物品、成長紀錄與事件序列一致
And 只根據合法的離線經過時間更新狀態
And 不會再次重複扣除上一筆食物
```

**E2E-03：個性與成長分歧**

```gherkin
Given 使用固定初始狀態、時鐘與亂數種子建立兩組測試
When A 組以頻繁玩耍／探索策略推進至成熟期
And B 組以休息／陪伴策略推進至成熟期
Then A、B 至少產生不同 growth_rule 或成熟分歧
And 每一組記錄的 growth_reason 可以追溯到輸入與狀態
And 重複執行同一組測試結果完全一致
```

**E2E-04：三鍵退回及防重複交易**

```gherkin
Given 玩家位於深度至少三層的選單
When 玩家連續按 C
Then 最終回到 Room 並保留合法狀態
When 玩家對單份消耗品連續按 B 五次
Then 只產生一次消耗與一次成功事件
```

**E2E-05：時間異常**

```gherkin
Given 存檔時間為 T
When 裝置時鐘變成 T-4h 並重新載入
Then 寵物沒有負年齡、負需求或額外收益
And 記錄時鐘異常
When 下一次有合法正向時間推進
Then 遊戲仍可繼續運作與存檔
```

### 10.3 驗收紀錄欄位與缺陷優先級

每筆驗收需記：`AC ID`、`build/commit SHA`、`平台`、`測試者`、`日期`、`前置狀態`、`操作步驟`、`預期結果`、`實際結果`、`Passed/Failed/Blocked`、`證據連結`、`缺陷 ID`。

- **Critical**：資料永久遺失、裝置無法啟動、危險電源／安全問題、核心玩法完全不可用。
- **High**：三鍵導覽卡住、誤扣道具、存檔不一致、成長錯誤、常態崩潰。
- **Medium**：偶發回饋缺漏、UI 裁切、非核心選單問題。
- **Low**：微小視覺錯誤、文案修正、非阻擋問題。

Release Gate：以「該里程碑適用的 P0 AC」為準，全部 Passed；Critical/High = 0；NFR 達到對應里程碑門檻；變更和已知限制有文件。實機專屬 `AC-ARCH-02/05/06` 延至 M5，不阻擋 M3 的 Mac MVP。

## 13. 風險、限制與應對

| ID | 風險 | 影響 | 緩解方式 |
|---|---|---|---|
| R-01 | Catode32 核心仍含板級／顯示／存儲耦合 | 直接 fork 的重構成本可能比預期高 | M0 優先做架構審核；必要時只移植經驗證的純函式或重做核心 |
| R-02 | ESP32-C6 與 S3 架構／HAL 不同 | 編譯 target 與驅動不共用 | 平台 Port，CI 多 target 編譯，硬體實測 |
| R-03 | 240×240 RGB565 全屏緩衝佔用約 115,200 bytes | 低 RAM 裝置易溢位 | 分區繪製、DMA 緩衝、壓縮資產；S3 PSRAM 候選 |
| R-04 | 中文字體及動畫資產佔 Flash | 容量／FPS 風險 | 子集字型、asset manifest、載入策略、真機量測 |
| R-05 | 真實時間改動／斷電／存檔故障 | 進度不合理或毀損 | 注入 Clock、推進上限、schema、備份與故障注入 |
| R-06 | 角色美術／商標授權 | 法律／公開發行風險 | 只用原創商標與素材；保留開源 MIT 授權告知 |
| R-07 | 一開始全做線上與社交 | 範圍膨脹、資安風險 | P3 獨立 Gate，不阻擋離線 MVP |

## 19. PRD v1.1 補充需求：健康、託管與雲端交付

### FR-17｜健康異常與復原（P0 / M2–M3）

**使用者故事**：當寵物因長期飢餓、清潔差或睡眠不足而不舒服時，我能辨認問題，使用適當的照顧方式讓牠逐步恢復，且不會在短時間離線後遭遇不可逆懲罰。

**規則**：`health` 0..100，不直接由 UI 賦值；其變化由需求與時間、照顧事件決定。需至少有 `healthy | unwell | recovering` 三個健康狀態；以不同進入／退出門檻避免邊界閃爍。首版不實作不可逆死亡。`CARE_HEAL` 僅在符合條件時消耗有效藥品或觸發可用的照顧操作。全部數值由 `game-balance.toml` 提供，不硬寫入 UI。

- `AC-HEALTH-01`：正常狀態連續照顧 24h（加速模擬）不得無故出現 `unwell`；固定低需求 fixture 可觸發 `unwell`，且日誌指出原因。
- `AC-HEALTH-02`：`unwell` 時房間顯示清楚提示，狀態頁可見原因；提示不只靠顏色或音效。
- `AC-HEALTH-03`：有效照護能讓健康依規則改善並進入 `recovering`，恢復至解除門檻後才回 `healthy`。
- `AC-HEALTH-04`：藥品不足／不可使用時拒絕執行，健康與背包均不改變，並顯示原因。
- `AC-HEALTH-05`：快轉、存檔與重新載入後，疾病／復原結果可重現；重送治療命令不會重複扣道具。

### FR-18｜臨時託管（P1 候選 / M4）

**範圍**：提供短暫無法操作時的低負擔照顧。此為本專案原創規則，不照搬 Uni 的託管時間或收費設定。

- `AC-SITTER-01`：玩家可設定託管開始／結束，顯示託管狀態和返回時間。
- `AC-SITTER-02`：託管期間需求依配置獲得有限保護，不產生重複領獎或加倍成長。
- `AC-SITTER-03`：託管結束與手動取消只結算一次；重啟載入仍能恢復正確狀態。
- `AC-SITTER-04`：不合法的開始時間、重複開始或超出上限應拒絕並給明確原因。

### FR-19｜雲端開發、版本控管與可測試交付（P0 基礎設施 / M0–M3）

**目的**：確保開發不被個人 Mac 的未提交檔案綁住。GitHub 保存程式與文件；CI 自動建置；測試者從可驗證的 Release／Artifact 取得 Mac 測試包；Web Preview 若規劃為必交項，使用與 Mac 相同的遊戲核心契約，不另寫一套不同的成長規則。

- `AC-CLOUD-01`：PRD、README、core、模擬器及 CI 設定均已提交至已授權的 GitHub repository，提交記錄包含 commit SHA；Git email 不代表使用者已授權 GitHub 帳號。
- `AC-CLOUD-02`：任何 PR 都會執行 `cargo fmt --check`、lint、單元測試與整合測試；失敗會阻擋合併。
- `AC-CLOUD-03`：標記測試版 tag 後，CI 產出 Apple Silicon Mac 測試包（壓縮檔／app bundle 依技術驗證決定），附 SHA-256、版本與執行說明；從乾淨 Mac 解壓可啟動。
- `AC-CLOUD-04`：公開或授權測試者可在雲端取得最新成功建置的測試產物，不需開發者從個人電腦手動傳檔。
- `AC-CLOUD-05`：如果啟用瀏覽器 Preview，鍵盤 A/B/C、存檔、核心規則與同種子事件重放和 Mac 版本一致；不同環境儲存位置有清楚告知。
- `AC-CLOUD-06`：程式庫與公開 Release 不包含密碼、Access Token、私鑰、個人本機路徑、真實玩家存檔或非授權素材；PR 需通過 secrets/license 掃描。
- `AC-CLOUD-07`：任一版本能從指定 git tag/commit 搭配鎖定依賴重建；記錄 Rust toolchain、OS/SDK 版本與建置指令。
- `AC-CLOUD-08`：目前尚未連上 GitHub／CI／Web Preview 前，所有雲端項目狀態必須為 `Not started` 或 `Blocked`，不能以文件存在視為交付完成。

### FR-20｜替代輸入、顯示與硬體抽象（P0 架構 / M1；實機 M5）

- `AC-PLATFORM-01`：同一組 `GameCommand` 在 Mac、測試 mock 與首個實體板卡產生相同核心狀態／事件；例外須明列並記錄版本。
- `AC-PLATFORM-02`：`game-core` 不依賴 SDL2、SPI、GPIO、ESP 特定 HAL；至少 Mac `cargo test` 可獨立執行。
- `AC-PLATFORM-03`：替換 C6/S3 Adapter 的編譯目標與板卡設定時，不能修改生長規則、商店經濟或性格 AI 實作。
- `AC-PLATFORM-04`：顯示器掉線、儲存失敗、按鍵卡住有可觀察錯誤／回復機制；至少在 mock 平台完成故障注入測試。
