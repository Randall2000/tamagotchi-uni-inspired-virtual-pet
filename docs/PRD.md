| [BALANCE.md](BALANCE.md) | 所有遊戲數字（加幾分、冷卻幾秒、門檻多少）的**唯一來源** | 要知道確切數值、或要調數值時 |

規則：

- **本文件不寫數字**。需要數字時寫 BALANCE ID，例如「好感冷卻（B-BOND-02）」。改數值只改 BALANCE.md，避免兩份文件寫不同數字。
- 「應」＝正式需求；「建議」「候選」「待定」＝可在設計評審調整的提案，不能當成已完成功能。
- **優先級**：P0＝核心 MVP 必須；P1＝豐富化；P2＝硬體感知及裝置互連；P3＝連網服務。

- **驗收 ID**：Web 用 `WEB-*`；Mac／硬體用 `MH-M<里程碑>-<流水號>`。本文件寫的 `AC-*` 是需求編號，在 ACCEPTANCE_MAC_HW.md 的「來源 AC」欄可以搜尋到對應項目。驗收內容只寫在兩份 ACCEPTANCE 文件，不在本文件重複。
- 本文件不表示程式已建立或測試已通過；以驗收文件的狀態欄為準。

## 1. 專案摘要

### 1.1 一句話定位

受 Tamagotchi Uni **互動方式與養成深度**啟發、只用 A/B/C 三鍵操作的**原創全彩電子寵物**；角色有需求、好感、個性與自發行為，讓玩家短時間照顧、長期陪伴。

### 1.2 要解決的問題

1. 直接照搬 Catode32 的黑白 OLED、八鍵與既有遊戲功能，無法充分滿足以 Uni 為基準的體驗。
2. 若先做角色美術和硬體外殼，之後很容易因選單、動畫介面或記憶體限制而返工。
3. 沒有可執行版本及時間快轉／狀態注入工具，養成流程很難快速反覆驗證。
4. 程式若與 GPIO、顯示 IC、儲存方式耦合，後續更換板卡或螢幕就要大量重寫。

### 1.3 產品目標

| ID | 目標 | 放行標準（可量測） | 平台 |
|---|---|---|---|
| G-01 | 三鍵易學 | 未看教學的測試者 n≥5，至少 4 人在 60 秒內完成一次餵食 | Web、Mac |
| G-02 | 核心可玩 | 新遊戲→餵食→玩耍→清潔→睡眠→狀態→重新載入，全程無卡住 | Web、Mac |
| G-03 | 寵物有生命感 | 加速模擬 15 分鐘閒置，出現至少 3 種不同的自主行為，且沒有每幀來回切換 | Mac（Web 目前只有眨眼） |
| G-04 | 成長具有因果 | 成長階段只由好感決定（B-BOND-03），相同照顧序列兩次結果相同；外觀分支待 D-11 | Web、Mac |
| G-05 | 核心可攜 | 同一份核心規則在 Mac 與至少一種 ESP32 平台共用，不使用平台特定 GPIO API | Mac、HW |
| G-06 | 開發可迭代 | 替換正式 Sprite 不修改核心遊戲邏輯 | Web、Mac |

### 1.4 設計原則

- **Uni 為體驗標竿，不是資產來源**：學習三鍵操作、人格與喜好、照顧循環、家居、裝扮、探索等概念；不複製 Bandai 角色、圖像、UI 素材、音效、文案或商標。
- **一致、可預測、可回復**：A 選擇、B 確認、C 返回；選取狀態清楚；操作失敗一定顯示原因。
- **低負擔陪伴**：允許短暫離線，不刻意造成高壓或懲罰；離線補算有上限（B-TIME-01）。
- **可測試**：時間、亂數、存檔、輸入都可在測試中注入。
- **數值集中**：遊戲數字只放在 BALANCE.md 與對應設定檔，不散落在 UI 程式。

## 3. 使用者、場景與核心循環

### 3.1 目標使用者

- 喜歡 Tamagotchi 類型養成與像素美術的玩家；每天多次、每次 30 秒至 5 分鐘的碎片化使用。
- 希望觀察角色反應、影響性格與成長分支的玩家。
- 自製硬體與程式開發者；希望不依賴特定板子先在 Mac 驗證，再移植實機。

### 3.2 核心循環

`啟動 / 觀看房間 → 看到需求或角色自主行為 → A 選擇照顧 → B 確認 → 狀態改變 → 動畫/音效/文字回饋 → 累積喜好與成長紀錄 → 返回房間`。

長期循環：`每日照顧 → 累積偏好和養成評分 → 進入下一階段 → 解鎖新的行為／互動 → 留存紀錄`。

## 4. 產品資訊架構（IA）與三鍵互動

### 4.1 Web 現行畫面結構（v0.8）

```text
房間（主畫面）
└─ 底列 6 個捷徑（A 輪選、B 執行；螢幕上的圖示不能點）
   ├─ 餐食 → 直接開始吃
   ├─ 清潔 → 直接開始清潔
   ├─ 玩耍 → 直接玩毛線球
   ├─ 摸摸 → 直接摸摸
   ├─ 狀態 → 需求條、好感、距長大差額、冷卻（只能看）
   └─ 選單（只有一層）
      ├─ 睡覺／點心／洗臉／伸懶腰／看窗外 → B 直接執行
      └─ 設定 → 儲存進度／重新開始（需二次確認）
```

**照顧動作不得再多一層選項**：底列的照顧按 B 立刻執行；其他動作放在選單第一層。互動完成或取消後，回到出發的畫面與游標位置。閒置時每 6–12 秒有一次小動作（B-ANIM-08），介面外觀依 B-UI-01 一律像素風。

### 4.2 Mac 版目標結構（M1–M3，待設計評審）

Mac 版沿用 4.1 的底列一鍵動作模式，另加：啟動畫面（新遊戲／繼續）、Debug 面板（僅開發版）、P1 以後的道具／房間／外出／商店入口。尚未開發的選項在開發版標示「開發中」，不得導向空畫面；發行版直接隱藏。

### 4.3 按鍵語義（全平台一致）

| 輸入 | 房間 | 選單／清單 | 確認對話框 | 動作播放中 | 睡眠中 |
|---|---|---|---|---|---|
| `A` | 底列下一個捷徑，末項回第一項 | 下一項，末項回第一項 | 切換選項 | 只顯示「動作進行中」提示 | 只顯示喚醒提示 |
| `B` | 執行選中的捷徑 | 確認／進入 | 確認目前選項（預設停在安全選項） | 無作用 | 喚醒 |
| `C` | 無作用 | 返回上一層，保留上層游標 | 取消並返回 | 取消動作，不結算 | 喚醒 |
| 長按 | Web 無；Mac/HW 待定（B-INPUT-03） | — | 不得觸發危險操作 | — | — |

- 螢幕本身不接受觸控或滑鼠（B-INPUT-04）。
- 防連按依 B-INPUT-02。
- 任何畫面連按 C 最後都會回到房間。
- 「無項目」「狀態不允許」等情況一定顯示文字原因，不可靜默失敗。

## 5. 功能需求（P0）

每條需求的驗收項目見「驗收」欄指向的文件；數值見 BALANCE.md。

### FR-01｜開局、角色初始化（P0）

- 應建立 1 個本機存檔與 1 隻初始寵物；初始數值依 B-STAT-03。
- 重新開始會覆蓋進度，必須二次確認，預設選項是「保留進度」。
- Mac 版另需啟動畫面（新遊戲／繼續），同一 seed 與設定建立的新遊戲狀態相同。
- **平台**：Web（重新開始確認已實作）、Mac。**驗收**：WEB-NAV-04；AC-INIT-*。

### FR-02｜三鍵輸入與導覽（P0）

- 遊戲只認識抽象事件 A、B、C；鍵盤或實體按鍵的對應在適配器處理（B-INPUT-01）。
- 應有防連按、重複輸入保護；動畫中重複按 B 不可重複結算。
- 導覽規則依 §4.3。
- **平台**：Web（已實作）、Mac、HW。**驗收**：WEB-NAV-*、WEB-INPUT-*；AC-INPUT-*。

### FR-03｜需求與狀態（P0）

- 需求：飽足、心情、清潔、精力、健康（Web 尚無健康，B-STAT-02），範圍與初始值見 B-STAT。
- **好感不是需求**：獨立、永久累積，時間與需求下降都不會扣好感（B-BOND-01、B-DECAY-06）。
- 需求隨時間變化依 B-DECAY；由遊戲時鐘計算，不在 UI 每幀直接扣數值。
- 需求低時顯示提示（B-STAT-04）。Mac 版需有進入／解除兩個門檻，避免提示閃爍。
- 狀態頁顯示所有需求的名稱與數值、好感、距下一階段差額、加分冷卻。
- **平台**：Web、Mac。**驗收**：WEB-CARE-*、WEB-GROW-06；AC-STAT-*。

### FR-04｜照顧操作與回饋（P0）

- P0 照顧：餐食、點心、清潔、洗臉、玩耍（毛線球）、摸摸、睡覺；另有不改數值的伸懶腰、看窗外。效果、位置與拒絕條件見 B-ACT、B-INPUT-05。
- 每次照顧：播放動畫（B-ANIM）→ **完成後結算一次** → 顯示結果文字（含好感變化）→ 回到原選單。
- C 取消：播放收勢、**不結算**、顯示「數值未變更」。
- 狀態不允許時（例如已吃飽、精力不足）拒絕並顯示原因文字，數值不變。
- **沒有背包的版本（Web v0.6、M2）不扣食物數量**；食物庫存與「沒有食物」的拒絕，等 FR-11 背包（P1／M4）上線才驗收。
- **平台**：Web（已實作）、Mac。**驗收**：WEB-CARE-*；AC-CARE-*。

### FR-05｜時間、睡眠與離線推進（P0）

- 遊戲時鐘可注入；載入時依經過時間補算，有上限（B-TIME-01：Web 240 分鐘；Mac 待 M2 平衡測試）。
- 時鐘往回調：補算 0，需求、成長、冷卻都不倒退（B-TIME-02）。
- 睡眠：選單→休息進入；睡眠存檔保留；B 或 C 喚醒（B-TIME-05）。自動起床與作息排程待定（B-OPEN-01）。
- Mac 版另需：Debug 快轉 1h／24h／7d 不改系統時間；睡眠時段由時區與設定推導。
- **平台**：Web（補算上限、回撥、睡眠已實作）、Mac。**驗收**：WEB-TIME-*；AC-TIME-*。

### FR-06｜自主行為 AI（P0／M3）

- 用有限狀態機加評分（或等效可解釋規則）決定行為，**不是隨機輪播動畫**。至少支援 `idle`、`walk`、`inspect`、`play_alone`、`seek_food`、`seek_attention`、`rest`、`sleep`、`groom`、`react_happy`、`react_unhappy`、`react_favorite`。
- 優先順序：睡眠／嚴重需求 > 玩家互動回應 > 高需求行為 > 個性偏好 > 閒置；分數接近時用可重現的 seed 亂數；不可每幀重抽。
- 每次決策可輸出原因（例如 `energy_low`），行為以 `behavior_id` 對接素材。
- **平台**：Mac（Web 目前只有待機眨眼）。**驗收**：AC-AI-*。

### FR-07｜好感、性格、喜好與成長（P0）

- **成長規則（已定案，D-05）**：三階段，幼年→成長中→成年，門檻依 B-BOND-03；只看永久好感，只前進不倒退、不跳階；年齡只顯示日數。
- 好感來源：成功的正向照顧（B-ACT 的好感欄），所有行為共用加分冷卻（B-BOND-02）。
- 舊存檔轉換依 B-BOND-06，更新後不得縮小。
- 長大時必須明確告知玩家：回到房間、角色慢慢放大並顯示慶祝畫面（B-ANIM-11），不能只在提示列閃過。
- 階段外觀尺寸固定，動作期間不改變尺寸；切換階段只換外觀素材，不改核心資料結構。
- 性格傾向（建議 `activity`、`curiosity`、`sociability`、`independence`，0–100）與物品喜好影響行為評分與反應；成年外觀分支待 D-11，不在 P0。
- **平台**：Web（好感與三階段已實作）、Mac（性格、喜好）。**驗收**：WEB-GROW-*；AC-GROW-*。

### FR-08｜存檔與資料正確性（P0）

- 存檔包含需求、好感、成長、時間、冷卻、睡眠；Mac 起另含性格、喜好、物品、亂數狀態與 schema 版本。
- Web：瀏覽器本機存檔（B-TIME-04），壞資料載入不當機、數值夾回範圍。
- Mac：先寫暫存檔再原子改名，保留上一份備份；實機用雙槽或等效做法。核心規則不得直接呼叫檔案系統。
- 至少一條舊版→新版 schema 轉換，資料不可無聲遺失。
- **平台**：Web、Mac、HW。**驗收**：WEB-SAVE-*；AC-SAVE-*。

### FR-09｜全彩 UI、素材接口與繁體中文（P0）

- 邏輯畫布 240×240；Mac／實機色彩預設 RGB565，由平台適配器轉換。
- 選取狀態不能只靠顏色辨識；P0 所有非 Debug 文案為繁體中文，過長時換行或截斷，不遮擋操作區。
- 動畫以素材 ID 查表；缺素材時顯示預設圖形並記錄警告，不當機。
- Web 角色動畫規格見 B-ANIM 與 [ANIMATION_V2.md](ANIMATION_V2.md)。
- **平台**：Web、Mac、HW。**驗收**：WEB-UI-*、WEB-ANIM-*；AC-UI-*。

### FR-10｜Mac 模擬器與 Debug 工具（P0／M1–M3）

- Apple Silicon Mac 優先；視窗用 SDL2 或經 M0 驗證的等效方案。正式畫布與 Debug 面板分離。
- Debug：單步、時間快轉、指定需求／性格、固定 seed、事件日誌匯出、重設測試存檔，以及至少 5 個固定情境（剛出生、飢餓、精力低、成年門檻前、損壞存檔）。
- Debug 命令不能被正式版一般三鍵誤觸。
- **平台**：Mac。**驗收**：AC-DEV-*。

### FR-17｜健康異常與復原（P0／M2–M3）

- `health` 0–100，由需求、時間與照顧事件決定，UI 不能直接改。
- 至少三種狀態：`healthy`、`unwell`、`recovering`；進入與退出用不同門檻避免閃爍。首版不做不可逆死亡（D-06）。
- 治療只在符合條件時消耗有效藥品或觸發照顧；不足時拒絕並顯示原因。
- 數值見 B-HEALTH-01（待定，M2 決定）。
- **平台**：Mac（Web 尚未實作）。**驗收**：AC-HEALTH-*。

### FR-19｜雲端開發、版本控管與交付（P0 基礎設施）

- GitHub 保存程式與文件；每次推送自動跑測試；Web 預覽由 Vercel 連結 GitHub `main` 自動部署。
- 一鍵上傳：`npm run ship`，測試沒過就不上傳。
- Mac 版：打 tag 後 CI 產出 Apple Silicon 測試包，附 SHA-256 與執行說明。
- 程式庫與公開產物不得含密碼、Token、私鑰、個人路徑、玩家存檔或未授權素材。
- Web 與 Mac 若同時存在，同一段錄製的按鍵與時間序列，核心結果應一致；目前 Web 為 JavaScript、Rust 核心尚未共用，此項在 Mac 版完成前無法執行（NOT RUN）。
- **平台**：Web（已實作）、Mac。**驗收**：WEB-DEPLOY-*；AC-CLOUD-*。

### FR-20｜替代輸入、顯示與硬體抽象（P0 架構／M1；實機 M5）

- 核心不依賴 SDL2、SPI、GPIO 或 ESP 專屬 HAL；Mac 上可獨立跑核心測試。
- 同一組遊戲命令在 Mac、測試 mock 與首個實體板卡產生相同狀態與事件。
- 更換板卡設定時，不得修改成長規則、經濟或性格 AI。
- 顯示器斷線、儲存失敗、按鍵卡住要有可觀察的錯誤與回復機制，至少在 mock 平台做故障注入。
- **平台**：Mac、HW。**驗收**：AC-PLATFORM-*、AC-ARCH-*。

## 6. 擴充功能（P1–P3）

驗收項目見 [ACCEPTANCE_MAC_HW.md](ACCEPTANCE_MAC_HW.md) 的 M4–M6。

### FR-11｜背包、物品、商店與遊戲貨幣（P1 / M4）

**需求**：物品以 `item_id`、`category`、`stack_limit`、`effect_id` 定義。貨幣採不可為負的整數，商店價格由資料表提供。首版建議至少 5 種食物、3 種玩具、3 種家具、3 種配件；僅用原創佔位資產。

### FR-12｜小遊戲與貨幣獎勵（P1 / M4）

**需求**：先實作 1 種完全原創、三鍵即可操作、單局 30–90 秒的小遊戲，輸贏回饋清晰。獎勵配置可調整，防止中斷重送刷幣。

### FR-13｜房間、家具與配件（P1 / M4）

**需求**：房間使用 `room_id` 與固定槽位定義（如牆面、地面、玩具、裝飾）；寵物可依喜好與擺放物品互動。角色配件和基本動作以獨立圖層呈現，正式美術未完成前使用色塊。

### FR-14｜散步、材料收集與 DIY（P2 / M5）

**需求**：散步功能先依賴抽象 `MotionSource`，提供模擬步數產生器；實機有對應 IMU 或其他感測器時再介接。配方使用 `recipe_id`，所有合成交易原子化。

### FR-15｜近距離裝置互動（P2 / M5）

**需求**：離線裝置間互動（例如 ESP-NOW 或其他適合晶片的通訊）須先有明確相容性設計。第一版限模擬器協定測試，不承諾跨所有板卡能互通。資料交換只包含必要角色資訊／交換物品，不暴露裝置 Wi-Fi 密碼。

### FR-16｜Wi-Fi 更新、線上活動與遠端內容（P3 / M6）

**需求**：網路功能為獨立模組，離線遊戲是預設完整體驗；雲端帳號、OTA、活動、安全與合規需另立安全設計文件後才能上線。不得在 P0 偷渡未授權外部服務或 API Key。

### FR-18｜臨時託管（P1 候選 / M4）

**範圍**：提供短暫無法操作時的低負擔照顧。此為本專案原創規則，不照搬 Uni 的託管時間或收費設定。

## 7. 工程架構（跨開發板、先模擬器）

### 7.1 分層及相依規則

```text
            ┌────────────────────────────────────────────┐
            │           Game Application Layer           │
            │ Navigation · Commands · Events · Scene VM  │
            └────────────────────┬───────────────────────┘
                                 │
            ┌────────────────────▼───────────────────────┐
            │              Pure Game Core                │
            │ Pet · Needs · AI · Growth · Economy · Time │
            │ No GPIO / SPI / Wi-Fi / SDL direct imports │
            └────────────────────┬───────────────────────┘
                                 │ interface / traits
        ┌──────────────┬──────────┼───────────┬──────────────┐
        ▼              ▼          ▼           ▼              ▼
    DisplayPort     InputPort   ClockPort  StoragePort     AudioPort
        │              │          │           │              │
    ┌───┴──────────────┴──────────┴───────────┴──────────────┴────┐
    │ Adapters: Mac(SDL2) / ESP32-C6 / ESP32-S3 / future hardware│
    └──────────────────────────────────────────────────────────────┘
```

**硬性約束**：

1. `game-core` 必須可在主機上以 `cargo test` 單獨測試；不可直接依賴 `esp-hal`, `ssd1306`, `mipidsi`, `sdl2`、GPIO 或串口。
2. `GameCore::update(delta, commands, rng)`（示意介面）採確定性狀態轉移，回傳 `events`；不得直接操作螢幕。
3. `GameController` 將 A/B/C 與導航狀態轉成命令；畫面層只消費讀取模型與 `visual_event`。
4. `StoragePort`、`ClockPort`、`RandomPort`、`InputPort`、`DisplayPort` 皆可測試替換；音效及震動可以為 No-Op 適配器。
5. ESP32-C6 與 S3 不共用特定 HAL 實作，但共享事件／導航／核心規則；S3（含 PSRAM 型號）為**優先評估**而非當前已定案硬體。
6. 顯示器邏輯解析度為 240×240；變更硬體顯示器型號只替換平台顯示驅動，若實際畫布不同則需變更 UI layout config，不能保證所有螢幕尺寸零修改。
7. 為避免 ESP32 記憶體限制，應在 M0 決定 `no_std + alloc` 或受控 `std` 策略，並在實機測量 heap/stack；不得假設 macOS 記憶體表現能代表裝置。

### 7.3 領域模型與資料契約（概念）

| Entity | 最少欄位 | 規則 |
|---|---|---|
| `PetState` | `pet_id`, `species_id`, `stage`, `appearance_id`, `needs`, `personality`, `likes`, `age_simulated` | ID 穩定，UI 不依賴圖檔 |
| `Needs` | `satiety`, `happiness`, `hygiene`, `energy`, `health` | 整數 0..100；可隨時間及照顧行為變動 |
| `Bond` | `points`, `growth_stage` | 好感點數只由正向互動增加；階段只前進，時間及需求衰減不會扣除 |
| `Personality` | `activity`, `curiosity`, `sociability`, `independence` | 整數 0..100，可平衡調整 |
| `BehaviorState` | `behavior_id`, `started_at`, `deadline`, `cooldown_map` | 可中斷、可復原 |
| `GrowthRecord` | `stage`, `stage_entered_at`, `rule_id`, `growth_reason` | 可追蹤成長原因 |
| `Inventory` | `items`, `currency`, `applied_transactions` | 不可負值、交易冪等 |
| `WorldState` | `local_timezone`, `last_simulated_at`, `room_id`, `time_of_day` | 以注入 Clock 推進 |
| `SaveSnapshot` | `schema_version`, `saved_at`, `pet`, `world`, `inventory`, `rng_state`, `checksum` | 版本化、備援恢復 |
| `VisualEvent` | `asset_id`, `animation_id`, `message_key`, `priority` | 不包含實體圖檔路徑 |

**命令與事件範例（純示意）**：

```json
{
  "command_id": "cmd-00042",
  "type": "FEED_PET",
  "payload": { "item_id": "food_basic_01" }
}
```

```json
{
  "event_id": "evt-00106",
  "type": "PET_FED",
  "payload": {
    "item_id": "food_basic_01",
    "need_changes": { "satiety": 18 },
    "visual_event": "pet.eat.normal"
  }
}
```

**實作備註**：上面是 domain contract 草案，不要求真實韌體內部一律序列化 JSON；如使用 `serde`，需要評估 embedded 目標大小、記憶體及序列化可靠性。

### 7.4 遊戲時鐘、規則引擎、可重現性

- `WallClock` 提供現實日期／時區；`SimulationClock` 提供遊戲 delta；兩者不可混用。
- 需求變化不綁 FPS，建議每固定遊戲時間步長積分；動畫可獨立渲染更新。
- AI 決策需使用可注入 RNG 並保留可重現 seed／必要狀態；只固定 seed 但改變事件呼叫順序仍可能不同，測試必須固定完整事件順序。
- 時間大幅快轉與分段推進的結果允許依規則有小差異，但必須建立一致性測試與容忍值；同輸入應保證結果一致。
- 所有敏感交易、成長與時間異常都應寫 structured event 便於除錯。

### 7.5 顯示與動畫資產規格

| 類別 | 草案規格 | 驗收方式 |
|---|---|---|
| 畫布 | 240×240，RGB565 | 模擬器與目標 LCD 同座標 |
| UI | 繁體中文、可辨識焦點、無裁切 | 截圖快照＋人工檢查 |
| 基礎角色圖 | 暫用 48×48 / 64×64 佔位方塊 | 渲染器不依賴最終大小 |
| 動畫 ID | `pet.idle`, `pet.walk`, `pet.eat.normal`, `pet.sleep` 等 | 缺 ID 回退，不 panic |
| 正式圖片 | 之後再做獨立 Sprite Sheet、透明色策略、配件圖層 | 資產 Pipeline 單獨驗收 |
| 更新策略 | 優先區域刷新；不假設存在整張 framebuffer | 在裝置上以 profiling 決定 |

## 8. 硬體策略與相容矩陣

### 8.1 硬體選型狀態

| 項目 | 目前狀態 | 決策或限制 |
|---|---|---|
| 主控晶片 | **未定案**；ESP32-S3 + PSRAM 優先評估，ESP32-C6 候選 | 選型前不把特定晶片 HAL 寫入核心 |
| 螢幕 | ST7789 1.54 吋 240×240 SPI 候選 | 確認接線、背光、電壓與驅動 IC |
| 輸入 | 3 個實體按鍵 A/B/C | GPIO 編號待選板後確定 |
| 聲音 | 蜂鳴器或小型喇叭（後續） | P0 可以 No-Op，語意回饋不得依賴聲音 |
| 時間 | 桌面系統時鐘；實機 RTC/網路校時候選 | 離線時仍須可靠推進或明示時鐘限制 |
| 電源 | 初期 USB；電池及充電後續 | 不在未經檢查的自製電路直接接鋰電池 |
| 動作感測器 | P2 候選 IMU | 未選型前只使用 `MotionSource` mock |

### 8.2 跨平台契約的驗收

- `AC-ARCH-01`：`game-core` 源碼搜尋無直接 MCU HAL、SDL、GPIO 引用；主機獨立單元測試通過。
- `AC-ARCH-02`：同一錄製的輸入事件／時間／seed，Mac 與設備（或 cross-target core harness）產出相同重要遊戲狀態；時間與浮點差異須由定義處理。
- `AC-ARCH-03`：更換 `DisplayPort` 的 mock，角色需求／成長單元測試結果不變。
- `AC-ARCH-04`：更換鍵盤映射／GPIO 腳位時，不需要修改導航狀態機。
- `AC-ARCH-05`：實機於 60 分鐘連續操作與畫面更新後無崩潰、看門狗重啟或持續增長的記憶體使用量（測試條件記錄在案）。
- `AC-ARCH-06`：第一次支援的 MCU 選型決策有可重現的編譯／資源量測紀錄與原因，未經測試不得宣稱支援。

## 9. 非功能需求（NFR）及量測方法

以下數字是**提議的工程門檻**，需在 M0 用選定硬體與基準測試確認；若實測不可達成，應透過變更單調整，而非默默降低品質。

| ID | 類別 | 初始驗收門檻 | 量測方式 |
|---|---|---|---|
| NFR-01 | 反應 | Mac：按鍵到可見畫面回饋 p95 ≤100ms；實機目標 p95 ≤150ms | 測 100 次，採第 95 百分位 |
| NFR-02 | 畫面 | Mac 目標 30fps；實機先以穩定 ≥15fps 為最低門檻，目標 ≥20fps | 60 秒代表性房間／選單／動畫測試 |
| NFR-03 | 記憶體 | 正常運作時不產生記憶體溢位；韌體 heap 高峰不得超可用 heap 80%（初版安全預算） | 逐場景記錄 RAM、PSRAM、stack、heap 峰值 |
| NFR-04 | 穩定性 | Mac 連續 2h 自動操作無 crash；實機 1h 無 watchdog reset | soak test、保留 log |
| NFR-05 | 存檔 | 100 次存檔／載入循環，全部資料合法且一致；故障注入可恢復前一可用檔 | 自動化＋故障注入 |
| NFR-06 | 離線啟動 | 不需網路連線或外部帳號即可開始遊戲與儲存 | 關閉 Wi-Fi 測試 |
| NFR-07 | 可讀性 | 240×240 無主要資訊重疊、選單焦點無歧義，圖示有文字或可識別回饋 | 多頁面快照、人工審查 |

## 13. 風險、限制與應對

| ID | 風險 | 影響 | 緩解方式 |
|---|---|---|---|
| R-01 | Catode32 核心仍含板級／顯示／存儲耦合 | 直接 fork 的重構成本可能比預期高 | M0 優先做架構審核；必要時只移植經驗證的純函式或重做核心 |
| R-02 | ESP32-C6 與 S3 架構／HAL 不同 | 編譯 target 與驅動不共用 | 平台 Port，CI 多 target 編譯，硬體實測 |
| R-03 | 240×240 RGB565 全屏緩衝佔用約 115,200 bytes | 低 RAM 裝置易溢位 | 分區繪製、DMA 緩衝、壓縮資產；S3 PSRAM 候選 |
| R-04 | 中文字體及動畫資產佔 Flash | 容量／FPS 風險 | 子集字型、asset manifest、載入策略、真機量測 |
| R-05 | 真實時間改動／斷電／存檔故障 | 進度不合理或毀損 | 注入 Clock、推進上限、schema、備份與故障注入 |
| R-06 | 角色美術／商標授權 | 法律／公開發行風險 | 只用原創商標與素材；保留開源 MIT 授權告知 |
| R-07 | 一開始全做線上與社交 | 範圍膨脹、資安風險 | P3 獨立 Gate，不阻擋離線 MVP |
| R-08 | 現實養成測試耗時 | 回歸測試慢、難重現 | Debug time travel、seed、fixture、事件 replay |
| R-09 | 太多數值但無法理解 | 玩家不知道該做什麼 | 首頁只呈現必要提示，狀態頁分層顯示；可用性測試 |

## 15. Definition of Ready（DoR）／Definition of Done（DoD）

### 一張功能票可開始實作之前（DoR）

- [ ] 明確標註 Ticket / FR / AC / 優先級 / 前置依賴。
- [ ] 有成功、失敗、取消、無資料與邊界輸入情境。
- [ ] 介面契約與資料範圍可寫單元測試。
- [ ] 若依賴硬體或外部服務，提供 mock 或定義為 Blocked。
- [ ] 任何不確定的遊戲平衡數值寫在配置檔，而非散落硬編碼。

### 一張功能票可標記完成之前（DoD）

- [ ] 所屬 AC 全 Passed，測試輸出與 commit SHA 可追溯。
- [ ] 核心邏輯有正向／逆向／邊界測試，CI 通過。
- [ ] 無未處理 panic、資料不一致或不可恢復的錯誤路徑。
- [ ] 繁體中文文案可讀，A/B/C 互動可往返。
- [ ] Debug log 不洩露秘密；正式版未暴露測試入口。
- [ ] README、架構文件、變更紀錄與測試情境已同步。
- [ ] 無 Critical/High 缺陷；已知 Medium/Low 有記錄與 owner。
